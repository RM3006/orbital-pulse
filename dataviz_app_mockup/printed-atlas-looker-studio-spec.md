# Printed Atlas implementation in Looker Studio

This spec translates the five Printed Atlas pages into components available in the no-cost edition of Google Data Studio (Looker Studio). The **proposed native build** in each section is the starting design for a private report. Alternatives are choices for review. The native settings are based on Google’s documentation and the prior private build evidence in [Roadmap Step 5](../ROADMAP.md#step-5--private-data-studio-dashboard). The configuration in this document still needs to be verified in report view.

- [Design spec](printed-atlas-design-spec.md) and [interactive reference](printed-atlas-design-export/printed-atlas.html) define the visual intent and the five reference states.
- [Data spec](printed-atlas-data-spec.md) defines the warehouse relations, metric logic, and expected results for the **11 Nov 2026 UTC** edition. This spec names additional SQL output fields as proposed aliases.
- Use this document for Looker Studio component selection, control scope, and layout. Where it proposes an adaptation, record the selected option in the build handoff and compare the rendered result with the corresponding reference PNG.

### BigQuery sources and release handling

For the private design comparison, pin the retained reporting relations to `sla-release-v1-d4f4ae640e0934f11d7ad4c4`. Bind the lookup for launch names and providers to the matching snapshot described in the data spec. Use the BigQuery connector with existing authorized access. | --- | --- |

| Launch outcomes | `mart_launch_attempt_daily`, `mart_family_outcomes_daily`, and the matching provider/configuration/family dimensions. One row per release, grouping mode, and entity ID (including an unknown bucket when needed). |
| Site totals and site months | `mart_site_cadence`. One row per release and site for the map and gap table. Separate source with one row per release, site, and UTC month for the pivot. |
| Flight history and landing outcomes | `mart_booster_flight` with `launch_labels` for the flight source, at `(release_id, booster_id, launch_id)`. Separate `mart_landing` summary at release and outcome grain, including explicit zero for a missing outcome category. |
| Manifest | `mart_upcoming_schedule`, `launch_labels`, and `core_dim_provider`. One row per release and `launch_id`. Separate context queries return full-horizon precision totals and coverage. |
| Edition copy and coverage | `mart_data_coverage` plus the independent aggregates cited on each page. For dynamic narrative, return one row per release per story query. Aggregate each input to its own grain before combining one-row results. |

Keep `release_id` and `input_snapshot_id` in the prepared SQL. Use both for release-scoped joins and `(input_snapshot_id, launch_id)` for the frozen source lookup. Protect the chart grain when joining names. Configure preaggregated numeric fields explicitly as `SUM` for additive counts and `MAX` only when the visual grain guarantees one valid source value. Keep unsupported values null and format them as a dash. Preserve genuine zeros. Use UTC consistently, including for displayed timestamps and calendar bins.

For a production report that follows new releases, first expose names and provider IDs through the existing release process and bind all chart and narrative sources to the same approved edition. Update or regenerate edition-specific copy with its source values. Looker Studio can cache chart queries separately, so validate the release and edition date across sources after refresh. Keep the previous validated edition available for rollback. The frozen design check can use static text tied to the pinned data. Query-result variables are an option for refreshed copy. Confirm their behavior with controls in the reader before using them for filtered counts. ## 7. Reader checks for the private build

Use [Step 5](../ROADMAP.md#step-5--private-data-studio-dashboard) to track implementation progress. Use the following checks to compare the result against this spec. Start with Upcoming and Reuse, where the visual adaptations affect the story most.

1. **Upcoming.** In View mode, All returns 179 and Year returns 129. The count and manifest update together while the full-horizon bars and coverage retain their totals. Compare a minute, month, and year entry. Confirm a broad interval that extends before the horizon clips at its start, and a broad interval past the horizon clips at its end. Confirm the original text remains unchanged. Check visible labels for unknown scope and unsupported precision.
2. **Reuse.** B1067 gives 37 recorded flights and 29 supported turnaround intervals. B1063 gives 36 and 27. The strip and log change together. Missing turnaround stays a dash, and the landing total stays 709. Verify that a daily aggregation is labeled as such and that the log keeps individual flights.
3. **Overview and outcomes.** Toggle to 1957 and back. The comparison table and elapsed-year bars remain fixed. Check totals **113 / 324 / +211**. Verify all three grouping modes, separate IDs for duplicate display labels, the correct classified denominator, and access to rows after the first eight.
4. **Spaceports.** Check all six markers, compare Cape Canaveral SFS and Vandenberg SFB, ensure both heatmap and gap table stay fixed during site selection, and compare a zero month and the maximum count against the underlying data. Verify the same count means the same color wherever a common legend appears.
5. **Visual review.** Capture all five default pages in View mode at the 1,440 px canvas setting, with the report language and date formatting checked.
