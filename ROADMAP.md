## Release scope

**Release 1:** launch activity, providers/vehicles, reliability, spaceports, reuse, upcoming schedules and methodology/freshness. Steps 0–5 deliver this release.

**Release 2:** detailed satellite and spacecraft views, with reviewed source linkage and payload coverage. Step 6 delivers this expansion.

### Warehouse contracts

Use the existing six layer names (`source`, `staging`, `core`, `marts`, `reporting`, `scratch`). Terraform owns APIs, datasets and access; dbt owns analytical tables/views; the pipeline owns inputs, load jobs and release state. Source/candidate rows carry `input_snapshot_id`; retained reporting rows will carry `release_id`. Those identifiers extend each table's business key rather than changing its grain.

| Model group | Grain/key and required behavior |
|---|---|
| Launch current and launch attempts | One row per launch ID per snapshot/release. Keep current schedules separate from qualifying orbital attempts; preserve unknown scope and unresolved outcomes. |
| Providers, vehicles, families and sites | One source entity per ID; configuration-family bridge uses the pair of IDs. Family membership filters must preserve distinct launch counts. Current source geography/labels are not asserted as historical attributes. |
| Stage flights and landing associations | Stage flight key is launch ID + stage-flight ID. Keep hardware IDs, null reuse flags and landing attempt/outcome separate from launch outcomes. Do not derive historical flights from all-time counters. |
| Observation history and upcoming schedules | Stable event identity for observations, preserving repeated returns to earlier content. Upcoming is one launch per frozen horizon, selected by supported precision interval overlap; retain unsupported precision as coverage. |
| Release 1 marts | Launch growth, provider share, launch reliability, site cadence, booster reuse, supported turnaround/landing outcomes and upcoming/coverage/freshness. Apply [metric contracts](docs/metrics.md); ratios use summed numerators/denominators. Sparse hardware history must not imply consecutive flights or complete turnaround coverage. |
| Release metadata and reporting views | One metadata row per release, one active-pointer row, and release-scoped reporting rows. Every reporting view selects the same active release and has no dependency on mutable candidate/source tables. |

### Publication and failure rules

1. Pin the input snapshot, code/model versions, frozen as-of and extraction completeness before building a candidate. Unfinished required windows or unresolved blocking conflicts prevent release eligibility; never turn a partial extraction into a successful complete refresh.
2. Build and validate candidate tables before touching the active release. Enforce keys/relationships, known statuses, null/coverage policies, date bounds and independently checked denominators. Compare volumes with the prior release using documented tolerances; surface legitimate source changes for review.
3. Materialize all retained reporting rows for the new `release_id` before selecting it. Keep permanent table/view creation outside the publication transaction; BigQuery transactions do not support permanent DDL. Update validated release metadata and the pointer together using DML, with an expected-previous-release check to reject stale publishers. [BigQuery transaction rules](https://docs.cloud.google.com/bigquery/docs/transactions). The no-billing sandbox does not support DML; the user's active Free Trial is billing-associated and the user authorized bounded BigQuery DML testing. The design still needs a post-trial alternative.
4. If publication fails, the previous pointer remains selected. First-publication failure serves no release. Rollback selects an earlier retained validated release without rebuilding against changed source data. Test reader behavior before and after pointer changes.
5. Warehouse release consistency does not promise simultaneous Data Studio chart refresh. Keep a release ID and freshness fields available for the report/cache checks in Step 5. No public report, website change or notification automation is part of Step 3.
