# Metric contracts

These contracts define the implemented release 1 SQL and its coverage limits. Current execution evidence and release eligibility live in [ROADMAP.md](../ROADMAP.md). Historical acquisition remains incomplete; no worldwide completeness claim follows from a successful model build.

| Metric | Numerator / denominator | Scope, grain, time and exclusions |
|---|---|---|
| Orbital attempts | Distinct qualifying launch_id | LL2 orbital-filtered source AND supplied non-suborbital mission orbit; status 3/4/6/7/9, nonfuture nonnull NET. Suborbital and unknown-scope records excluded; unknown scope reported as coverage and may undercount legitimate attempts. Time is source NET in UTC; not asserted to be independently measured liftoff. |
| Launch success share | Success / (success + failure + partial failure) | Attempt grain and selected NET window; partial failures displayed separately, not counted as success. In-flight/deployed unknown outcomes remain in attempt totals and are exposed as unresolved, excluded from classified denominator. Never return 0% for an empty denominator. |
| Provider attempt share | Provider attempts / all scoped attempts | Same time window and denominator, including unknown provider in the total. Not revenue or market value. |
| Landing success share | SUM(successful_landing_count) / SUM(known_landing_outcome_count) | One landing ID per snapshot, deduplicating repeated stage associations. Only qualifying orbital attempts; require landing_attempt=true and a known outcome. Conflicting source associations are excluded from counts and exposed by source_fields_consistent. Preserve unknown outcomes separately. Return null when the denominator is zero. |
| Booster reuse share | SUM(reused_flight_count) / SUM(reuse_known_count) | One identifiable hardware ID per qualifying orbital launch; repeated stage associations collapse before counting. Require nonplaceholder identity and supplied reuse flag. Contradictory flags/flight numbers are excluded from the denominator. Null reuse is unknown. Publish identifiable-flight and source-detail coverage. This is a hardware-flight share. |
| Turnaround | Difference between consecutive supported flights of the same hardware ID | Require consecutive positive source flight numbers, second/minute launch precision, consistent associations, increasing NET, and agreement with the source previous-flight timestamp when supplied. Sparse sequences and coarse dates yield null duration; never assume the previous observed flight is consecutive. Source duration strings remain available unchanged in the stage mart but are not parsed as measured durations. |
| Site cadence | Attempt counts and gaps between observed attempts at one site_id | One attempt row preserves the launch denominator. Gaps require second/minute/hour precision for both observed attempts; unknown sites/dates yield null gaps. history_complete remains visible: gaps in an incomplete extraction do not establish actual site inactivity. Pad and location are separate grains; current geography is not historical sovereignty. |
| Upcoming manifest | Distinct eligible launch IDs whose supported NET precision interval overlaps [frozen_as_of, frozen_as_of+90 days) | `fact_upcoming_schedule` is launch grain, one row per launch ID per export horizon. Store the source NET placeholder and `[schedule_earliest, schedule_latest_exclusive)` interval; include month/quarter/half-year/year candidates when their intervals overlap. Unsupported precision remains in the coverage counts and is excluded from this fact. The bounded acquisition envelope is intentionally broader than the final interval filter. This is a schedule-uncertainty window, not an exact launch schedule. |
| Schedule movement | Signed seconds between consecutive accepted schedule-interval starts at the same fine precision | Events retain their own raw-backed NET/precision, ordered by accepted observation sequence. Only equal second/minute/hour/day precision is comparable. Positive means later, negative earlier; this does not classify a launch outcome. First observations, unsupported/coarse precision and refinements have null movement with an explicit comparison_basis. No schedules are reconstructed before project observations. |
| Payload count / mass | Source-linked recorded entries with coverage and estimation flags | Deferred. Empty arrays and descriptions cannot establish actual total payload count/mass. |
| Freshness | Completed refresh, source update, observation, release creation and activation times separately | mart_data_coverage exposes last_complete_refresh_utc, latest_source_update_utc and latest_observation_utc. Reporting views expose reporting_analysis_as_of_utc, reporting_published_at_utc and reporting_activated_at_utc plus release_id. A partial backfill sample is not a completed full refresh. Chart caching can preserve an earlier release independently. |

Future comparative views: full available history from 1957, primary comparisons from 2000. Compare current year to the same elapsed previous-year period. Always display classified denominator/sample sizes and unresolved counts. Store additive numerators/denominators in marts; compute ratios from their sums under filters. Do not average percentages, use Top-N as a total, or sum counts across overlapping family memberships.

## Authored mart grains

- `mart_launch_attempt_daily`: one row per snapshot, UTC launch date, provider, configuration and site. `attempt_count` and outcome counts are additive across those dimensions; group by null provider/site/configuration rather than dropping unknowns.
- `mart_family_outcomes_daily`: one row per snapshot, UTC launch date and family. Each row counts distinct launches within that family; counts are non-additive across families because configurations can belong to multiple families.
- `mart_stage_flight`: one row per snapshot, qualifying orbital launch and source stage-flight association. It preserves source hardware/landing values; unflown associations are excluded.
- `mart_upcoming_schedule`: one supported launch schedule per snapshot horizon, retaining source precision and its derived half-open interval.
- `mart_booster_flight`: one row per snapshot, launch and identifiable hardware ID, with additive reuse numerator/denominator counts and supported turnaround.
- `mart_landing`: one row per snapshot and landing ID, with separate attempt/known/success/unknown counts and source-association consistency.
- `mart_site_cadence`: one row per snapshot and orbital launch, retaining unknown sites and explicitly observed gaps.
- `mart_schedule_movement`: one row per snapshot and observation_event_key, preserving non-schedule events, unsupported comparisons and A-to-B-to-A histories.
- `mart_data_coverage`: one row per snapshot with independent counts, history completeness and distinct freshness fields; no composite quality score.

Retained reporting tables extend each key with release_id. Dimension/bridge views are retained with the same release so labels and family membership cannot drift after activation. dbt tests exercise nonempty examples for partial/unresolved outcomes, duplicate associations, missing reuse, sparse/coarse turnaround, unknown landings/sites, precision refinement and unflown stages, alongside model-key, coverage and volume checks.
