# Decisions

| ID | Decision | Evidence / rationale |
|---|---|---|
| 001 | Keep the supplied folder `orbital-pulse`; package/repository metadata uses `space-launch-atlas` / `launch_atlas`. | The original handoff was copied into the active project brief at bootstrap. | 004 | Add tzdata only on Windows. | Nonempty tests exposed ZoneInfoNotFoundError for UTC when Polars exported timestamp rows. Windows lacks the system IANA database; adding the runtime dependency fixes real timestamp reads. |
| 005 | argparse and per-run filesystem state; no application server. | First consumer is the reproducible ingestion CLI. One canonical path, no extra service. Explicit local mode rejects cloud mode and unverified source URLs. |
| 006 | Smoke budget 2; general explicit runs capped at 8; source-wide local ledger capped at 15/hour. | Conservative default for interactive verification, leaving shared-IP headroom. Retries consume the same budget. 429 stops with persisted Retry-After; long transient waits checkpoint rather than sleeping indefinitely. |
| 007 | Keep raw and normalized output per run; no global metric publication. | Required first deliverable is replayable public data, not an empty dashboard. Per-run correction/semantic dedup is implemented; persistent cross-run observations and watermarks belong to Step 2. |
| 008 | Retain GCS + BigQuery + dbt and Dagster + GitHub Actions as the production proposal; defer installation/provisioning. | No billable resources authorized. Adding adapters without SQL or a warehouse consumer would not validate them. Step 1 contains the working local dependency chain; add Dagster around it when that graph becomes useful. |
| 009 | MIT for project code; attribute The Space Devs data separately. | Brief's default retained. Public fixtures are reduced source data; images retain separate licenses and are not rendered. Recheck terms before publication. |
| 010 | CI checks Windows and Linux; pinned third-party actions and uv. | Action SHAs verified with upstream refs on 2026-11-01. Workflow is authored, not executed remotely. Local Windows results are the current evidence. |
| 011 | Exclude unknown mission/orbit scope from the orbital denominator while retaining every raw/current record. | The full upcoming page returned three HASTE entries with mission=null despite include_suborbital=false. Rocket Lab's official HASTE page identifies the vehicle as suborbital. Source filtering alone is insufficient evidence for null-orbit records. Nineteen of the 106 upcoming source records lack an orbit; flag coverage and review in Step 2. This conservative policy can undercount legitimate unknown-scope launches; it does not invent orbital status from names or source counters. |
| 012 | Keep semantic hashes separate from response checksums. | Raw checksums cover all bytes. Within-run observation hashes use launch/schedule/status/mission identity, hardware-flight/landing fields and supplied payload structure; they exclude media, all-time provider/hardware counters and source-update-only changes. Every raw retrieval remains evidenced. |
| 013 | Put pytest's explicit temporary root at .pytest-tmp, directly under the checkout. | A real fresh-checkout test exposed that pytest does not create the parent of --basetemp data/test-tmp. The documented command and CI now work before any ingestion has created data/. |
| 014 | Use SQLite for local cross-run acquisition state; keep raw evidence filesystem-backed and Parquet analytical exports derived. | Step 2 transactions couple accepted acquisitions, current records, observations and window cursors without adding a service or runtime dependency. This is not the warehouse architecture. |
| 015 | Model semantic content versions separately from sightings and observation events; use semantic hash version 2. | Content hashes ignore media/counters but include schedule, status, mission/scope, stage/hardware and landing semantics. Event history retains A→B→A and same-content retrieval remains a sighting. |
| 016 | Map supported LL2 NET precision to half-open UTC intervals and select upcoming schedules by interval overlap. | Calendar boundaries are tested for second/minute/hour/day/month/quarter/half-year/year. Unsupported precision remains coverage and is not assigned an invented interval. |
| 017 | Freeze refresh/backfill plans and share one invocation budget across windows. | Recent lookback 30d, upcoming 90d, correction overlap 48h with five-minute cutoff; annual two-pass backfill with dense years split monthly over threshold. Windows and query config are persisted before acquisition. |
| 018 | Broaden the bounded correction query to include suborbital records and source-update filters. | The source's orbital-only filter can hide scope reclassifications; corrections preserve actual source scope and do not silently make an unknown record orbital. |
| 019 | Rebuild only complete live raw runs by default; offline imports require explicitly supplied run IDs. | Prevent fixture/demo imports from silently changing accepted state. Rebuild preserves the last completed refresh's frozen horizon from its completed manifests. |
| 020 | Export revisioned Parquet generations and change the active pointer only after validation. | A failed candidate must not replace the last good local reporting generation, matching the eventual release safety contract. |
| 021 | Select Data Studio (formerly Looker Studio) for reporting. | User confirmed 2026-11-07. This resolves the former BI-product question. Metric logic stays in dbt SQL; no Looker subscription, instance or LookML is planned. |
| 022 | Select Terraform for infrastructure; reuse the available CLI and initialize a local Google-provider harness. | User requested Terraform 2026-11-07, superseding the original brief's OpenTofu placeholder. CLI 1.13.1 was already installed; Google 7.46.2 is initialized/locked. At entry, one bucket and five datasets were locally declared and mock-tested. The configuration was later extended with access design under decision 030. No cloud apply, project, region or spending approval is implied. |
| 023 | Detailed satellite and spacecraft views belong to release 2. | User confirmed 2026-11-07. Release 1 remains launch analytics; detailed payload/object views require reviewed identifier/source coverage. |
| 024 | Use Step terminology and consolidate planning/status in ROADMAP.md. | User requested fewer documents and one roadmap. Removed the standalone execution plan, separate guide, duplicate bootstrap, setup file and handoff. Their useful scope/status/check/runbook content is retained in the brief, roadmap, README and operations doc. Keep source, metric and decision contracts separate; reuse existing docs for future work. |
| 025 | Give each accepted launch-observation event a stable versioned key. | Key v1 hashes the acquisition ID and record ordinal, preserving distinct A→B→A events across rebuilds without making source launch IDs the event key. Exported `launch_observation` declares this key and its launch/event grain. |
| 026 | Pin warehouse inputs with an immutable local snapshot before any upload/load. | Snapshot v1 verifies current SQLite revision, passing Parquet generation/checksums/row counts and accepted raw manifests/pages; it records source windows, reconciliation, coverage/as-of, parser/hash/key versions and transformation-code digest. The content ID excludes incidental generation IDs and creation timestamps, but includes relevant exported file checksums and horizon. It does not imply history completeness or cloud readiness. |
| 027 | Keep cloud/warehouse libraries in an optional locked `warehouse` dependency group. | Dagster, dagster-dbt, dbt Core/BigQuery and GCS/BigQuery clients resolve and import on Windows/Python 3.12 without credentials. dbt Core is constrained below 1.12: resolving 1.12 selected an experimental parser whose package build attempted a GitHub wheel download and failed certificate verification in this environment. No TLS setting was weakened; the installed/tested locked line is dbt Core 1.11.17 with dbt-bigquery 1.11.3. |
| 028 | Keep a Data Studio service account optional and disabled by default. | Google documents the service-account credential mode for BigQuery data sources only and limits eligibility to managed Google Workspace or Cloud Identity organizations. The user's account type is unknown; owner/viewer credentials remain alternatives. The Terraform template therefore defaults the optional identity off. [Requirements](https://docs.cloud.google.com/data-studio/data-credentials-article). |
| 029 | Do not apply the GCS/BigQuery/Data Studio template while no cloud usage is authorized. | At the time, the no-billing BigQuery sandbox appeared incompatible with the DML release pointer, and Data Studio's BigQuery connector required a billing-associated project. Decision 031 later authorizes bounded BigQuery work within the user's active Free Trial; this does not authorize Terraform apply, GCS, Data Studio or paid usage. [Sandbox](https://docs.cloud.google.com/bigquery/docs/sandbox), [Data Studio connector](https://docs.cloud.google.com/data-studio/connect-to-google-bigquery). |
| 030 | Extend the local Terraform template with separate warehouse access roles, required APIs, versioned raw storage and expiring scratch. | The mock plan declares six colocated datasets, a versioned private bucket, ingest/transform identities, dataset-level permissions and optional reporting-only read access. `validate` and four mock tests pass. This prepares configuration only; actual costs, IAM, account eligibility and deployment have not been verified. |
| 031 | Use the existing active Google Cloud Free Trial for BigQuery load and processing within its always-free limits. | User explicitly authorized BigQuery load/processing on 2026-11-07. The signed-in console showed an active trial and the project ID matched `GCP_PROJECT_ID`; `GCP_LOCATION=europe-west1`. Stay within 1 TiB query processing and 10 GiB storage per month; do not upgrade or consume trial credit beyond the free tier. Scope is BigQuery datasets/tables and jobs only: no GCS, Terraform apply, Data Studio, publication or other GCP services. On 2026-11-07 the console created four datasets, loaded the 11-table pinned snapshot (224,815 input Parquet bytes) and verified all table row counts against local files; the dataset DDL and initial count script reported 0 bytes. Job IDs and the final query's byte figure were not recorded. At the time this decision was recorded, the broader `cloud-platform` ADC grant had not been authorized; that authentication point is superseded by decision 034 without changing the authorized service-use boundary. [Free Trial FAQ](https://cloud.google.com/signup-faqs), [BigQuery pricing](https://cloud.google.com/bigquery/pricing). |

| 040 | Keep hardware/landing/schedule grains and coverage separate in release 1 SQL. | Deduplicate hardware per launch and landings per landing ID; exclude unflown associations. Turnaround needs consecutive source flight numbers and fine dates; schedule refinement is not a delay. Observation schedules come from each retained sighting, with a deterministic per-launch provenance sequence rather than SQLite global IDs. Nonempty dbt unit cases cover missingness, duplication, sparse/coarse history and outcome denominators. |
| 041 | Retain Dagster and diagnose its Windows stall as a sandbox loopback restriction. | A 20-second stack dump stopped in asyncio's socket-pair accept before the first op; the same probe succeeded outside the sandbox in about two seconds. The full job executes locally. Marked offline tests permit loopback only; no Windows security setting or OAuth scope change was needed. |
| 042 | Retain actual reporting rows and dimensions before atomic activation. | Nine marts and six dimension/bridge relations use release-scoped append-only rows, stable pointer-filtered views, schema/count checks and SHA-256 row-multiset digests. Manifest identities and retained data are rechecked on activation/rollback. BigQuery integration proves two data releases, old-reader independence, stale/failed publication, rollback and corruption rejection in expiring scratch. DDL stays outside transactions per [BigQuery rules](https://docs.cloud.google.com/bigquery/docs/transactions). |
| 043 | Use 100 MB per-query caps in the integrated runner and a separate 250 MB multi-view test cap. | Current data is small; preflight confirmed ample free query/storage headroom. A combined reader across 15 views touches 17 underlying tables and required 170 MiB under BigQuery's per-table billing minimum. The standalone dbt profile keeps its configurable 1 GB default. None of these per-job settings guarantees monthly/project-wide spend. |
| 044 | Shorten prepared snapshot directories while checking their full identity. | Deeper Windows test paths exceeded the native replace-path limit. A 24-hex prefix plus snapshot.json rejects prefix collisions and retains full snapshot/job identities. Load contract v3 also allows an explicit scratch source-dataset override for integration fixtures; normal source destinations are unchanged. |
| 045 | Run dbt in an isolated CLI subprocess within the Dagster chain. | Each invocation has unique aliases, profiles, target/log paths, a code-digest check and artifact/result validation. [dbt documents](https://docs.getdbt.com/reference/programmatic-invocations) global-state constraints on concurrent in-process calls. dagster-dbt remains installed/locked; the current job invokes the CLI directly rather than its resource wrapper. |
| 046 | Distinguish supplied stage fields from recorded stage-flight coverage. | Detailed LL2 responses can supply empty launcher_stage arrays. The legacy normalized stage_detail_available flag means key presence; the reporting coverage mart names that explicitly and independently counts distinct attempts with actual stage rows. Revision 42 has 16 flown stage associations across 14 attempts; these are not 16 launches or global hardware completeness. |
| 047 | Use the no-cost Data Studio edition without provisioning a BI server instance. | The free-only requirement excludes a Pro subscription. A personal Google account can author reports and use owner/viewer credentials. Managed Workspace/Cloud Identity adds administration and eligibility for the service-account credential mode; it is not necessary to create this portfolio report. The credential owner can differ from the report/data-source owner, allowing a dedicated user with reporting-only BigQuery access. The final credential principal remains undecided. [Product](https://docs.cloud.google.com/data-studio/welcome), [requirements](https://docs.cloud.google.com/data-studio/what-you-need), [credentials](https://docs.cloud.google.com/data-studio/data-credentials-article). |

The current Cloud Billing metadata API returned 403 and no permissions were expanded. [Free usage](https://cloud.google.com/bigquery/pricing), [extract limits](https://docs.cloud.google.com/data-studio/extract-data-for-faster-performance), [approximate quotas](https://docs.cloud.google.com/bigquery/docs/custom-quotas). |

The revision-42 dbt/candidate-check workload was 1.514 GiB per invocation; weekly over 31 days projects to about 6.7 GiB for that workload before full-history growth, publication and report/extract queries. The cadence is a target only: no schedule, Data Studio authorization, source or report was created. Verify that the selected query credential has read-only effective access; the owner's account may qualify if its existing IAM roles are suitably constrained. Complete history and a production release still gate the connection. Do not assume this estimate guarantees zero charges. |
